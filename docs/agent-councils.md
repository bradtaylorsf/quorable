# Investigative agent councils

The bounded controller described in the roadmap below is now available as
`quorable revise`, with `quorable readiness` for freshness rechecks. See
[revision loops](revision-loops.md) for the implemented contract. The
`investigate` command documented here remains advisory.

Quorable's best thesis is that independent, accountable investigations can
surface consequential mistakes that a single reviewer misses. The product
should help a person or another agent decide what to fix, what to verify,
and when enough evidence exists to proceed.

The existing engine is useful for repeatable rubric scoring. The new
`investigate` command adds a different execution model: each persona gets a
fresh agent session, access to the document's workspace, and instructions
to investigate evidence and check its own conclusions. Reviews and synthesis
are Markdown from the outset.

## Use it

Build the local CLI with `npm run build`. Install and authenticate the
harnesses you select separately. No Quorable API key is required for this
command; the harness uses its own authentication and billing.

```bash
node dist/cli/main.js investigate draft.md \
  --workspace . --context ./reference \
  --council general-doc \
  --agent codex --agent claude \
  --criteria 'For engineering leadership. Verify feasibility, ownership, rollout risks, and measurable acceptance criteria.' \
  --synthesizer claude --synthesizer codex \
  --final-synthesizer codex \
  --concurrency 3 --timeout 600
```

With an installed build, replace `node dist/cli/main.js` with `quorable`.
Use `--dry-run` first to inspect the assignments without launching agents.
Use `--persona skeptical_expert` to select one existing persona. Harness
specifications accept an optional model: `--agent codex:MODEL_ID` or
`--agent claude:MODEL_ID`. With no model override, the harness chooses its
configured model. Existing API reviewer/synthesizer model settings are not
used by this command.

The existing config discovery and persona/rubric libraries still apply.
`--criteria` adds the purpose, audience, requirements, and acceptance checks;
it does not replace the council's dimensions. Reference paths can be files
or directories. Paths are handed to agents for selective investigation;
Quorable does not concatenate the reference corpus into a giant prompt.

Every selected harness runs every selected persona. With three personas
and two harnesses, that is six review sessions. Review sessions run up to
`--concurrency` at a time. All finish before synthesis starts. Multiple
synthesizers run concurrently, followed by a final synthesis that receives
both their reports and references to the original reviews. An explicit
`--final-synthesizer` also adds this final pass with a single synthesizer.

## Artifacts and process semantics

Each invocation creates a fresh output directory. An explicit `--out` must
not already exist. The default includes a random run suffix.

| Artifact | Purpose |
| --- | --- |
| `brief.md` | Target, context paths, review criteria, investigation rules |
| `prompts/*.md` | Exact assignments, including persona overlays |
| `reviews/*.md` | Individual final responses; failed partial text is retained |
| `synthesis/*.md` | Each synthesis and, when applicable, final reconciliation |
| `synthesis_report.md` | Final narrative plus engine-generated coverage/status |
| `run.yaml` | Incremental job statuses, errors, timing, requested harness/model, primary hash |
| `traces/*.log` | Harness stderr when emitted; not guaranteed to be a complete tool transcript |

Reports use local finding IDs (F1, F2, …); cross-report references use the
report ID plus finding ID. Findings ask for a location, evidence,
counterevidence, fix, and acceptance check. Synthesis must account for
blocking findings individually, including any it refutes.

`run.yaml` is written by code, not generated by the model. It carries
execution status, not extracted opinions. Exit 0 means execution completed
(or assignments were prepared with `--dry-run`); exit 2 means incomplete;
setup errors exit 1. **Exit 0 does not mean ready to ship.** Readiness is
always `unassessed` in the manifest. The narrative recommendation is
advisory and may be ready, revise, or needs evidence.

Failed or empty reviews keep the run incomplete even if synthesis succeeds.
With zero successful reviews, synthesis is skipped. Timeout and cancellation
preserve completed reports; SIGINT/SIGTERM abort active jobs and cancel
queued work. On POSIX, termination kills the process group, including tool
children. On Windows only the immediate child is terminated. Output is
bounded to 8 MiB per subprocess across stdout and stderr.

The primary hash is checked again at completion; a changed or deleted
primary makes the run incomplete. References and workspace files are not
snapshotted or hashed. For reproducible evidence, supply a stable checkout.

## What is and is not enforced

The adapters use the documented noninteractive entry points:
[Codex exec](https://developers.openai.com/codex/noninteractive/) and
[Claude Code print mode](https://code.claude.com/docs/en/headless).
The local CLI help was also checked during implementation.

Codex runs in its read-only sandbox with approvals disabled. Claude gets
Read, Glob, Grep, WebSearch and WebFetch, with `dontAsk` and no configured
MCP servers; it cannot run shell tests through this adapter. Check the
[Claude CLI reference](https://code.claude.com/docs/en/cli-reference) for
flag details. These adapters deliberately do not pass permission-bypass
flags. Available research tools, network access, organization policy, and
authentication can still limit an investigation. Agents must report such
limits instead of claiming they verified something.

Fresh sessions separate conversation history. They do not prove statistical
independence or provide filesystem isolation between reviewers: agents
share the workspace, and the instruction not to read peer reports is a
prompt constraint. Harness configuration, project instructions, hooks,
plugins, and credentials may affect behavior. Use trusted workspaces and
separate checkouts/containers when stronger isolation is required.

A nonempty final response is accepted as prose; section completeness,
citation correctness, and actual evidence gathering are not automatically
validated. This command does not compute rubric scores, run mechanical
gates, measure agreement, run a held-out validator, or authorize shipping.
The existing `review` command remains the scored API workflow. Its `render`,
`validate`, `diff`, and `handoff` commands do not consume investigation runs.

Harness costs are unknown to Quorable (`cost_usd: null`), not zero. The API
cost governor does not apply. Concurrency and per-session wall-clock limits
are enforced; total dollars, tokens, and turns are not. This first version
has no automatic retries, resumable sessions, revision loop, or persistent
question-answer channel. Open questions become report content for the
caller to resolve.

## Review of the original architecture

The original implementation already had several strong objectives:

- Separate domain policy (personas and rubrics) from the engine.
- Preserve disagreements, reviewer failures, and traceable raw results.
- Compute aggregates and gates independently of the synthesizer.
- Distinguish verified claims from requests for validation.
- Evaluate blind spots through cold readers, held-out checks, and outcomes.

The principal problems are architectural rather than prompt wording:

1. **Reviewing is a fixed call, not an investigation.**
   `ts/src/engine/pipeline.ts` fans out jobs to `validatedCall` with assembled
   documents. `validation.ts` retries formatting failures; it does not let
   the reviewer choose sources or execute verification tools. Concurrency
   is already present; agency is what was missing.
2. **A large output schema gates access to otherwise useful criticism.**
   `validation.ts` returns null after exhausted schema repair attempts.
   `synthesis.ts` supports Markdown only after structured synthesis fails.
   This treats a presentation-format failure as loss of the review itself.
3. **Synthesis is both a bottleneck and a lossy layer.**
   `buildSynthesisMessages` embeds every review into one prompt. A summary
   can flatten disagreement or omit minority blockers. Multiple summaries
   can compound that loss unless the final stage retains access to original
   findings and sources.
4. **Computed does not mean objective.**
   `scoring.ts` computes aggregate scores from model-supplied ratings.
   Protecting arithmetic from the synthesizer is valuable, but the ratings
   and findings remain judgments. Vendor diversity and agreement statistics
   do not establish correctness. High agreement alone also does not prove
   redundancy; personas can independently discover the same real defect.
5. **Readiness needs evidence provenance across runs.**
   In `review.ts`, prior validation resolutions are carried forward by
   normalized claim text. A changed source can invalidate an old resolution
   even when that text matches. In `cli/commands/runs.ts`, standalone
   `validate` reads the current target and resolves current configuration,
   while comparing against an earlier synthesis. Bind these operations to
   the evaluated document and evidence versions.
6. **Run-directory reuse risks stale artifacts.**
   `review.ts` removes old raw review JSON, but retains earlier synthesis
   for comparison. When the new run uses Markdown fallback, it does not
   remove an earlier `synthesis.json`. Downstream commands can then see an
   older structured synthesis in the current run directory. The new command
   requires a fresh directory; the existing API path still needs this fix.
7. **The contract promises more orchestration than the shipped CLI has.**
   `CONTRACT.md` describes drafting and revision loops from the Python design.
   The TypeScript CLI exposes a single review flow. Treat loop orchestration
   as explicit future work rather than implying it already ships.

These findings come from source inspection. They are not claims that live
model quality or the historical errors on your documents were reproduced.

## The next architectural steps

Keep the CLI responsible for scheduling, artifact ownership, validation,
limits, and policy. Let agents investigate and adjudicate semantic questions.
Adding another agent for every deterministic operation would make the
system harder to audit without improving judgment.

**Next: a small decision record alongside each Markdown report.** Keep
reasoning in Markdown. Extract only what automation needs: stable finding
ID, severity, evidence references, verification state, acceptance check,
and disposition. Use a small validated YAML/JSON sidecar, with source
pointers, rather than wrapping the entire critique in JSON. If extraction
fails, keep the report and mark the decision incomplete. Never derive a
ship decision by searching prose for the word “ready.”

**Then: targeted investigation rounds.** The synthesizer should propose
specific follow-up jobs for consequential disputes or missing evidence.
The engine should validate and schedule those requests with a total job,
time, and spend budget. Preserve the first independent round; mark later
rounds as informed by peer findings. A second round must have a concrete
question that could change the decision.

**Then: a bounded revision controller.** Start with a caller-managed loop:
review → inspect handoff → revise a separate document version → review
again. Give the controller explicit terminal states: ready, needs evidence,
needs user input, stalled, exhausted, and failed. Stop on no material change,
repeated findings without new evidence, iteration limit, or budget limit.
Recheck prior blockers against new evidence. Keep a held-out evaluator
outside the optimization loop so the system does not train itself to please
its final judge. Do not implement `while verdict != ready`.

**Validate the thesis with defect-detection experiments.** Compare the
current API panel, one investigative agent, and a council under matched
cost/time budgets. Use documents with known consequential defects and clean
controls. Include defects discoverable only in reference files, plausible
false accusations, conflicting references, missing evidence, and prompt
injection in source material. Measure supported-defect recall, false-positive
rate, citation accuracy, unverified assertions presented as facts, blocker
retention through synthesis, reviewer dropout, latency, and cost per useful
finding. Human adjudicators should not know which system produced a finding.
The new no-network tests establish orchestration reliability, not that
agent councils improve those quality measures.
